# Architecture Decisions

### D1 — Vector store: FAISS IndexFlatIP (exact) over ANN / pgvector

- **Options:** FAISS IndexFlatIP (exact brute-force inner product); FAISS IVF/HNSW (approximate); pgvector (Postgres extension); no separate index (embed at query time)
- **Choice:** FAISS IndexFlatIP
- **Rationale:** Approximate search introduces its own recall error, which would be an uncontrolled variable in a retrieval strategy comparison. The benchmark isolates strategy quality differences — ANN approximation error would contaminate that signal. FAISS runs in-process (no server), and exact search over a 300-paper corpus adds negligible latency.

### D2 — Embedding model: BAAI/bge-base-en-v1.5, fixed as a controlled variable

- **Options:** bge-small-en-v1.5 (faster, lower quality); bge-base-en-v1.5; bge-large-en-v1.5 (slow on CPU); OpenAI text-embedding-3 (API cost); per-strategy embeddings
- **Choice:** BAAI/bge-base-en-v1.5, identical across all five strategies
- **Rationale:** The embedding model must not vary across the ablation — it is a controlled variable, not a treatment. Differences in strategy scores then reflect only retrieval logic. bge-base balances quality and CPU-only inference speed at this corpus scale.

### D3 — Chunking: token-recursive 512/64, paper-level parent pointers

- **Options:** Character-based splitting; fixed token windows; token-based recursive (LangChain RecursiveCharacterTextSplitter); semantic chunking; sentence-level
- **Choice:** Token-recursive, 512 tokens / 64 overlap, with paper-level `parent_id` stored on every chunk
- **Rationale:** Token count is the natural unit for embedding model context windows. Recursive splitting preserves paragraph/sentence boundaries within the budget. Paper-level parent pointers enable parent-document retrieval as a future enhancement without re-indexing. Chunk size and overlap are part of `Config.fingerprint()`, so the provenance chain catches accidental changes.

### D4 — Retriever interface: `@runtime_checkable Protocol` with composition

- **Options:** Abstract base class with subclasses; plain Protocol; plain functions; dataclass dispatch on strategy name
- **Choice:** `@runtime_checkable Protocol` with composition — rerank, hybrid, and HyDE wrap a base `Retriever` rather than re-implementing retrieval
- **Rationale:** Protocol allows structural typing without inheritance coupling. Composition for composites means the benchmark loop never branches on strategy type — every strategy satisfies the same `retrieve(query, k) → RetrievalResult` contract. Runtime checkability enables `isinstance` checks in tests without a concrete base class.

### D5 — Generator/judge model separation: two complementary judges, different family, temperature 0

- **Options:** Same model for both generation and judgment; different providers; RAGAS only; custom rubric only; human evaluation only
- **Choice:** Claude / Anthropic (family A) generates answers; GPT-4o / OpenAI (family B) judges via two complementary mechanisms at temperature 0: (1) RAGAS stock metrics (faithfulness, answer_relevancy, context_precision, context_recall) run batch over all answerable examples; (2) a custom per-example rubric judge — correctness (0–2 vs reference answer), completeness (0–2 vs reference answer), citation_valid (bool: do the cited chunk ids actually contain the specific claim, not merely a topically related passage). Grounding is not a rubric dimension — it would duplicate RAGAS faithfulness.
- **Rationale:** Self-preference bias is a documented LLM-as-judge failure mode. A different model family for both judges removes this confounder. RAGAS covers grounding and relevance; the custom rubric covers what RAGAS does not: factual correctness against a reference answer, completeness, and citation honesty — whether the cited chunk actually contains the claim rather than being tangentially related. Temperature 0 ensures determinism on both sides. **Validation (n=40 blind human labels, dense strategy run):** correctness κ=0.70 (85% agreement), completeness κ=0.74 (90% agreement), citation_valid κ=0.33 (77.5% agreement). Correctness and completeness show substantial agreement; the judge skews slightly lenient on correctness (accepts right-fact/loose-framing answers humans marked partial). The citation_valid κ=0.33 reflects rubric ambiguity — "plausibly supports" is underspecified. On 5 of 10 citation_valid disagreements the judge was stricter than the human, correctly flagging factually-right answers whose cited chunks do not contain the specific claim; this is a real grounding failure the human missed. The ambiguous wording is a documented limitation of the current rubric.
- **Criterion sharpened (post-validation refinement):** the ambiguity was that the prompt scored a citation valid if the chunk *"plausibly supports"* the claim — conflating topical relevance with claim-containment. The rubric prompt now requires the cited chunk to **state or directly entail** the specific claim, with worked examples. Because this sharpening *moves the bar* rather than merely rewording it, the n=40 κ figures above (measured under the old wording, and lenient on ~5 real grounding failures) cannot re-validate the new criterion without a re-label; the committed κ stands as the pre-sharpening measurement. The rubric prompt is deliberately **outside** `prompt_template_hash` (which covers only the generation `system.txt`/`user.txt`), so sharpening the judge criterion does not perturb the gate provenance or the strategy-comparison fingerprint. Separately, κ = 0.33 is depressed by the 8/40 negative base rate — 77.5% raw agreement is the fairer read.
- **Judge-bias posture (three known LLM-as-judge biases, and how each is handled here):**
  - *Self-preference bias* (a judge favoring text from its own model family) — removed by construction: the generator is Claude/Anthropic (family A) and both judges are GPT-4o/OpenAI (family B), so no judge ever scores its own family's output.
  - *Ordering / position bias* (a judge favoring whichever candidate is shown first) — **not applicable** to this setup. Both judges do **direct, reference-anchored scoring** of a single answer at a time (RAGAS metrics per example; the rubric scores one answer against the reference). There is no pairwise or listwise comparison, so there is no candidate ordering for position to bias.
  - *Verbosity / length bias* (a judge rewarding longer, more elaborate answers) — mitigated on both sides. The rubric's correctness and completeness are scored **against a fixed reference answer** (whether the specific key facts are present/right), not against apparent thoroughness; RAGAS faithfulness and context-precision are grounding ratios that a longer answer cannot inflate (extra unsupported sentences lower faithfulness). Generation is also capped at `max_tokens=512`, bounding how much length a verbose answer could accumulate. Length is therefore not a free path to a higher score.

### D6 — Regression gate: provenance + floor + tolerance + operational ceiling

- **Options:** Manual review; simple threshold on one metric; multi-metric threshold; multi-check gate with provenance
- **Choice:** Four check types in sequence — provenance (config fingerprint / eval-set hash / prompt-template hash), quality floors (absolute minima), no-regression tolerances (Δ from committed baseline), operational ceilings (p95 latency, cost per query); tolerances calibrated from measured run-to-run noise (≈ 2 × std)
- **Rationale:** Provenance checks prevent comparing runs produced under different configs. Floors catch absolute quality collapse. Tolerances catch regressions while absorbing RAGAS judge stochasticity. Operational ceilings surface the latency/cost penalty of strategies that add a second model pass (hyde, rerank) — separating "passes quality" from "operationally viable" rather than masking the trade-off. **Calibration:** the p95 latency ceiling (185.71 ms) is 5× the committed dense baseline p95 (36.98 ms); rerank (~1 105 ms, ~30×) and HyDE (~11 445 ms, ~310×) intentionally exceed it — an explicit surfaced tradeoff, not a defect.

### D7 — Framework boundary: retrieval/indexing core is framework-free; LangChain for generation, chunking, and evaluation

- **Options:** Everything in LangChain; everything in LlamaIndex; LangChain for generation only; fully framework-free
- **Choice:** FAISS / rank-bm25 / sentence-transformers for indexing and retrieval search (no framework); LangChain for generation chain, chunking (text splitters), HyDE LLM call, and evaluation harness; LlamaIndex not used
- **Rationale:** The retrieval scoring core is what the benchmark measures — keeping it framework-free ensures results reflect the retrieval algorithm, not LangChain's retriever abstractions. LangChain is appropriate as a thin utility layer for generation (prompt templates, LCEL chains) and chunking (text splitters), where its abstractions don't interfere with measurement.

### D8 — Dependency pin: LangChain 0.3.x + ragas 0.2.x exact versions

- **Options:** Unpinned (latest); minor-version ranges; exact pins; separate virtual envs per experiment
- **Choice:** Exact-version pins for the entire LangChain 0.3 stack and ragas 0.2.15
- **Rationale:** LangChain 1.x + ragas 0.4.x is currently broken — ragas 0.4.3 hard-imports `langchain_community.chat_models.vertexai`, a path the 1.x-era community package removed, causing `import ragas` to fail on any provider. The 0.3 line + ragas 0.2.x is the mature, mutually-compatible combination. Exact pins ensure reproducibility across machines. Revisit when ragas ships LangChain 1.x support (ragas issue #2741 / PR #2739).

### D9 — CI scope: build-only; Docker Hub image published manually

- **Options:** Auto-push to Docker Hub on every merge to main (requires write-scoped token as repo secret); build-only CI + manual publish; no Docker in CI
- **Choice:** Build-only CI (`docker-build` job, `push: false`); Docker Hub image published manually
- **Rationale:** This repo has no deploy pipeline consuming the registry, so auto-publish adds a long-lived write-scoped token as a repo secret, a standing CI failure mode (red badge on registry or secret issues unrelated to code quality), and a second image build per merge for a convenience that won't be used. The manually-published public image at `leobergmiller/rag-evaluation:latest` and the README `docker pull` quickstart give a portfolio reviewer everything they need. Supersedes the `docker-push` CI job added in the initial Docker integration.

### D10 — Query scope: single-document-grounded QA; multi-hop / decomposition out of scope

- **Options:** single-document factual QA; multi-hop / multi-document synthesis; query decomposition / sub-question planning as a retrieval step
- **Choice:** the gold eval set is single-document-grounded questions — each answerable from one paper's chunks and carrying an explicit set of `reference_chunk_ids` — plus a minority of deliberately unanswerable questions that measure abstention. Multi-hop retrieval and query decomposition are out of scope.
- **Rationale:** The project measures *retrieval-strategy* quality under a controlled comparison, and single-document grounding is what makes that measurement clean. Each question has an unambiguous relevant-chunk set, so context-recall / recall@k / MRR / nDCG@k are well-defined and the harness can attribute a wrong answer to retrieval vs generation. Multi-hop questions would blur that attribution (partial-credit retrieval across hops, chained reasoning) and would introduce query decomposition as an *uncontrolled variable* that interacts differently with each strategy — contaminating the very comparison the benchmark exists to make. Query decomposition is therefore a deliberate non-goal: the absence of a decomposition step is a scope decision, not a missing feature. (HyDE, the one query transformation included, is a single embedding-time rewrite that keeps the one-question/one-relevant-set contract intact — it does not decompose the query.)

### D11 — Observability: structured per-run reports, no external tracer

- **Options:** an external tracing/observability platform (LangSmith / Langfuse / Phoenix); OpenTelemetry spans; structured per-example records persisted with each run; nothing
- **Choice:** observability is the structured data captured in every `StrategyReport` — per-example retrieved chunk ids, latency, abstention, RAGAS + rubric judge scores, and aggregate p95 latency / cost-per-query — written to `results/` as versioned JSON (plus the ablation report). No external tracer.
- **Rationale:** This is an offline benchmark harness, not a live service — there is no request stream to trace, and the unit of analysis is a full eval run, not an individual production request. The per-example report already captures what the experiment needs (retrieval-vs-generation attribution, latency, cost) reproducibly and diffably in version control, and feeds the gate and ablation directly. Adding LangSmith/Langfuse/Phoenix would introduce an external dependency and a second, non-version-controlled source of truth without answering a question the reports do not. If this system were promoted to serve live traffic, per-request tracing — and the online faithfulness sampling / drift monitoring deliberately excluded at this scope — would become worthwhile; at benchmark scope they are not. Consistent with the deliberate exclusion of live-traffic monitoring.

### D12 — Second corpus (PubMed Central medical literature) to demonstrate cross-domain generalization

> **Supersession note:** entries D1–D11 were written when arXiv was the *only* corpus and describe it as "the corpus." As of D12 the project runs over **two** corpora; wherever an earlier entry says "the arXiv corpus," read it as "each corpus" — the controlled-experiment design (D1–D9) is exactly what makes a second corpus a drop-in. The reasoning in those entries is unchanged; only the singular framing is superseded.

- **Options:** keep a single arXiv corpus; add a second domain by forking the codebase; add a second domain as a new config + ingest adapter through the existing pipeline
- **Choice:** a second, unrelated corpus — ~500 open-access PubMed Central full-text articles on immune-checkpoint inhibitors in cancer (JATS XML) — added as **`configs/config_med.yaml` + two ingest modules** (`ingest/pmc_download.py`, `ingest/jats_parse.py`) that feed the *existing* chunk → embed → index → retrieve → generate → evaluate → gate pipeline. Any entry point selects a corpus via the `RAG_CONFIG` env var (default arXiv). **Zero lines changed** in `retrieval/`, `generation/`, `evaluation/harness|report|rubric|judge|metrics`, or `gate/`.
- **Corpus identity:** both corpora deliberately share the same `config_fingerprint` (`defa37d5071c7049`) — the controlled variables (embedding, chunking, generation) are byte-identical, which is *the proof* that it is the same experimental setup. They are separated instead by `eval_set_hash`, `evaluation.baseline_path`, and `corpus.index_dir`. A medical candidate therefore fails the gate's provenance check against the arXiv baseline (different `eval_set_hash`), so the two corpora can never be silently cross-compared.
- **What it demonstrates:** the leading-3 strategy ranking by nDCG@k reproduces exactly across domains (`rerank > bm25 > hybrid`), cheap bm25 stays competitive in both, and rerank/hyde fail the gate on the latency ceiling in both — the earn-the-complexity finding generalizes. The one divergence, HyDE collapsing on medical (nDCG@k 0.62 → 0.37), is itself the point: the harness *catches* a strategy that doesn't generalize rather than assuming it does. See [../results/cross_domain.md](../results/cross_domain.md).
- **Scoped simplifications (transparent, budget-driven — "Option A"):** the medical run judges `faithfulness` + `context_recall` (the RAGAS metrics used in the cross-domain comparison and the gate) rather than all four; arXiv retains all four. Gate *tolerances* are reused from the arXiv calibration (judge run-to-run noise is a property of the judge + harness, both identical across corpora), with quality *floors* set from the medical dense baseline. Judge timeouts during the first medical batch reduced faithfulness sample coverage on two strategies (45–52 of 52), so faithfulness is reported but excluded from the medical gate's fine tolerance (its coarse absolute floor is kept). None of these touch the controlled variables or the fingerprint. Also unchanged and therefore reused as-is: the generation system prompt still says "machine learning papers" (D5) — keeping it byte-identical preserves the shared `prompt_template_hash`; the ML-worded framing is cosmetic on medical answers, and generalizing it would require re-baselining both corpora.
